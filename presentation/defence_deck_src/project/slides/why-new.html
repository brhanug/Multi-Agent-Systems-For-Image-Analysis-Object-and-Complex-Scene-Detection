Why each part is there

Object finder

The only agent that says where. Small and fast (0.06 s a picture), trained for this archive.

Scene matcher

Zero-shot: any class is asked as a sentence, no retraining when the class list changes; it can say “none fits”.

Describer

The strongest single model; one yes/no question per class gives a graded score for every class.

Learned mappings

Put three different scales onto one probability; few parameters, learned on training books only.

Risk promise

Turns “at most 5% wrong” into a cut-off with a guarantee, for any score.

A fixed procedure

Numbers, not chat between agents: the same answer every run, a score a promise can use, offline at no API cost.

Three agents also make the thesis testable: they let us measure whether disagreement warns of errors — and see where errors come from.

Part 3 of 5 · The corrected design

Why exactly these parts? The object finder is the only agent that says where an object is, and it is small and fast — 0.06 seconds a picture — and trained for this archive. The scene matcher is zero-shot: any class can be asked as a sentence, so when the archive’s class list changes nothing needs retraining, and because it scores each sentence on its own it can say “none fits”. The describer is the strongest single model, and asking it one yes/no question per class gives a graded score for every class. The learned mappings put these three different kinds of output on one scale, a probability, with very few parameters. The risk promise turns “at most five percent wrong” into a cut-off with a guarantee. And the agents exchange numbers through a fixed procedure, not a conversation like chat-agent frameworks: the same input gives the same answer every time, it produces a score that a statistical promise can be attached to, and it runs offline at no API cost. Finally, having three separate agents is what makes the central question testable at all.
